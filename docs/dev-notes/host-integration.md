## `py.typed`

**The annotations only reach integrators because of `src/dialectical_framework/py.typed`.** PEP 561: a type checker must IGNORE a distributed package's inline annotations unless that marker ships inside it, so without the file every rule above buys nothing outside this repo — an integrator running mypy or pyright sees `Advisor` as `Any` and no signature we write is checked at their end. It is an empty file and Poetry picks it up from the package directory with no `pyproject.toml` entry (verified in both the wheel and the sdist); `tests/test_packaging.py` guards it against a delete, because nothing else in this repo notices its absence. Added 2026-09-16 — it is NOT in the published 1.8.1, so typing support starts with the next release.

## Host-facing doc claims are pinned by tests

**The host-facing doc claims are PINNED BY TESTS, because nothing in `src/` depends on the docs being right.** `docs/graph.md`'s Events and Input Resolution sections and `docs/agents.md`'s obligation 3 hand an integrator four checkable facts, and all four used to be able to rot in silence: the bus payload is on `event.message` (the envelope is broadcaster's `Event`, only the framework's `GraphEvent` has `.effect` — the published snippet said `event.effect` and had been an `AttributeError` for as long as it was there); `publish`/`publish_progress` before `await bus.connect()` are a SILENT no-op, so a host that forgets to connect gets an empty stream with nothing to grep for; the DEFAULT resolver returns `https://…` verbatim, so a URL is analysed as its own 38 characters; and `agent.messages` serializes LOSSLESSLY by hand (`json.dumps([dataclasses.asdict(m) for m in msgs])`) because Mirascope's messages and content parts are plain dataclasses with `type`/`role` discriminators — `raw_message` must be kept, since `_strip_caller_from_messages` exists precisely because the provider gets it back verbatim. `tests/test_documented_host_seams.py` asserts all four against a real bus, the wired `container.input_resolver` and real Mirascope objects, with failure messages that name the doc to update rather than the code to fix. Mutation-verified where it counts: removing `publish`'s `_connected` guard fails exactly the silent-no-op test, and shows the mechanism — without it the call raises `AttributeError` out of broadcaster's `MemoryBackend`, so the guard IS the silence. **Two traps this file already warns about in other words, both hit while writing it:** grepping `src/` alone said `saved_at` is never read back and therefore "no reaper exists", when `scripts/cleanup_stale_nodes.py` is exactly that reaper and what is actually missing is a SCHEDULE and an in-process route (`docs/graph.md` says so now — grep the repo, not the package); and a count in prose drifts from a count in code, so "called from twelve places" became "injected in twelve modules" once one of them turned out to inject twice.

## Settings per request (2026-10-07)

**Why.** `container.settings` was one `providers.Dependency` slot filled by `setup()`, so the only per-person mechanism was `container.settings.override(...)`, which swaps the slot for every call in flight: two concurrent requests answered on each other's model. The first app (alsotrue) met it with a process-wide `asyncio.Lock` around every framework call — one card at a time per process — and sent a handoff. The bench had the same rule in `tests/e2e/modelctx.py` ("bench work must not run concurrently").

**What.** `settings_context.py` mirrors `scope_context.py`: a ContextVar over a process base. `setup()` calls `set_base_settings`; `container.settings` is `providers.Callable(get_current_settings)`, invoked on every resolution, so every `Provide[DI.settings]` and `SettingsAware.settings` read went per-request with no concern or agent touched. Precedence: `use_brain(ai_model=)` > innermost `using_settings` > base. `graph_db` is built from `container.base_settings`, deliberately: a Singleton built from the per-request provider would take whichever request resolved it first.

**The dual path is closed in code.** `_PerRequestSettings.override` raises naming `using_settings`; an override would have kept "working" by replacing the Callable with a fixed object and silently put the whole process back on one slot. Every override call site in tests and the bench (~10 files) moved to `using_settings(di_container.settings().model_copy(update=...))`.

**Alternatives set aside** (from the handoff): model-only ContextVar (fixes the symptom, leaves `component_length` and every future per-person knob in the trap); folding into `scope(sid, settings=)` (authorization vs configuration; the graphless Consultant has no sid); threading `model=` through every constructor (a missed one falls back silently, the same failure as a forgotten `with`, ten times the surface); a process pool per model (infrastructure per model).

**Checked and holds:** no client cache keyed by model (one Bedrock client per process, model per call); the framework's fan-out uses `create_task`/`gather`, which copy the context — re-check if a thread hand-off (`run_in_executor`) is ever added, it would drop the scope. Bedrock region is env-only, not in `Settings`, not covered. Tests: `tests/test_settings_context.py`.
