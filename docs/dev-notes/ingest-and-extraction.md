## Input digest, chunked reading, bounded consumption, the sweep

`Input.digest`: mutable field (excluded from hash) storing LLM-generated understanding of a source. Populated by `SourceDigest`; content <1500 chars skips the LLM (used as its own digest). **A source larger than one prompt is READ IN PARTS** (`utils/chunking.py`, `CHUNK_SIZE = 40_000` chars ≈ 10k tokens, overlapping windows): one reading per part, then one reduce over the readings (`PART_SYSTEM_PROMPT` / `COMBINE_SYSTEM_PROMPT`). Coverage is the guarantee, not best effort — a digest describing the first few pages while presenting itself as the understanding of the source is a lie nothing downstream can detect. Fitting sources keep the single-pass prompt byte-for-byte (`len(chunks) == 1`); each part gets a FRESH `ConversationFacilitator` (one shared conversation would re-accumulate the whole document in history); media is never chunked (branch on TYPE, not size). Whoever adds the input, digests it — via `ensure_digest()` (`concerns/source_digest.py`), the one fail-soft helper all three capture sites (`ingest`, `AnalysisPipeline`, the `add_input` tool) call. It takes a **hash, not the node**: `commit()` returns the caller's fresh object on a dedup hit, so mutable fields read as the caller's values, and deciding from the object re-digested on every capture. `refresh=True` only where there is a fresh intent to refine toward (`ingest`).

**Consumption:** skills use `input_context()` (`utils/input_context.py`) — digests in `<Input id="{hash}">` tags, falling back to resolved content when digest is None. **Bounded**: `INPUT_CONTEXT_BUDGET` (24k chars) is shared across all Inputs by water-filling, and a cut announces itself (`shown`/`of`/`truncated` + `"..."`); a source squeezed to zero is still named. Unbounded, this rendered 1.22 MB (~300k tokens) from three undigested 400 KB files into concern prompts of which five never truncate. Exception: `surface_theses` needs raw content for extraction (digest for previews only), so it does not go through `input_context` — it **SWEEPS** instead (below). Tools: `read_digest` | `read_input` | `digest_input` (Analyst and Explorer).

**Extraction sweeps; it does not select.** `surface_theses` chunks the concatenated source with the same `chunk_text` and, when it yields more than one window, runs `_extraction_sweep` instead of `_extraction_loop`: one `ThesisExtraction.extract_candidates` per window (capped at `MAX_CONCURRENT_WINDOW_SWEEPS = 3`, lower than the digest's 8 because each window is itself a fan-out of `count + 2`), candidates merged in document order with exact dedup, then ONE `classify_candidates` over the survivors. Why a sweep and not retrieval: extraction has no query — the theses are what is being looked for — so top-k against the intent string returns what the intent already anticipated and misses the tensions nobody thought to ask about. `ThesisExtraction` is split for this (`extract_candidates` writes nothing, `classify_candidates` writes the graph); sweeping with `resolve()` would commit a Statement plus a Rationale per candidate per window. Two deliberate behaviours: each candidate is classified against **its own window** (`classify_candidates` takes `(candidate, context)` pairs — `StatementClassification` truncates that context to 2000 chars, so one shared string places a page-300 claim using page 1), and under-delivery does **not** re-sweep (only a zero-candidate result under a focus earns one broader sweep, `artifacts["sweep_retried_without_focus"]`). Single-window sources keep `_extraction_loop` byte-for-byte. `StatementDeduplication` bounds its own `**Source Context:**` at `DEDUP_CONTEXT_LIMIT = 2000` (matching `StatementClassification`'s section of the same name) at BOTH prompt sites, which covers all four of its callers at once. Tests: `test_surface_theses_sweep.py`, `test_thesis_extraction_split.py`, `test_statement_deduplication_bound.py`.

## The declined step-2 source-elision lever

**The single biggest priced token lever on the ingest path is DECLINED after four A/B runs — treat it as closed, not as a to-do, and read WHY before reopening it.** `extract_candidates` reads in two steps: step 1 pulls content items out of the window, step 2 checks each item ONE CALL PER ITEM over `self._conversation.isolate()`, and `isolate()` copies step 1's history, whose request holds the whole window inside `<source_text>`. So a window is re-sent once per extracted item: **207,047 tokens across 24 calls on a 120 KB ingest, 75% of everything that document's size costs**, plus all 184,438 cache-write tokens with 0 reads (concurrent siblings under one `gather` write entries none of them can read back — the one shape prompt caching cannot serve, and not fixable with breakpoints). `settings.extraction_step2_carries_source` (default `True`, `DIALEXITY_EXTRACTION_STEP2_CARRIES_SOURCE`) is the knob, and `_step2_conversation` is the seam both arms go through; OFF rebuilds the SAME three messages in the same roles with `_SOURCE_ELIDED` where the window was, which is why `_step1_prompt` takes the source as a PARAMETER rather than having the finished string edited. **Two variants were A/B'd and both lost** (`tests/e2e/probe_step2_isolate_ab.py`, 2026-09-11 and 2026-09-17). A fresh conversation with NO history was rejected twice over: first because `is_substantive` flipped false-with-history to true-without, 5 times and 0 the other way on two 0.0% floors — an item that merely restates what the document established is not substantive and nothing in the item says so about itself — and then because it also cuts items finer, 22 of 72 items coming back `is_atomic` true-with-history and false-without, all one direction, yielding **18% more candidates** while agreeing with arm A on every keep/drop. Carrying step 1's ANSWER but not the passage is the arm that stays available, and it was run THREE times: **the same preregistered endpoints returned a different verdict each run — don't take, take, no call — on the same code and the same models.** What replicates is the saving (6.7-7.2x projected at `CHUNK_SIZE`) and the fact that the gate's keep/drop decision does not move at all (A-vs-C 0.0% in every run, 216 paired comparisons, on 0.0% floors). What does not replicate is the blinded judge on faithfulness: it leaned toward the source-carrying arm every run (pooled 19-6-11, 76% of decided) but its tie rate went 1, 6, 4 of 12 and its positional control went 62%, 47%, 73%, so the endpoint's pass/fail turns on how often it shrugs. Two instruments built to strip that confound both find nothing — equalising the two sets' sizes gives A 3 / C 4 then A 4 / C 4, and an unpaired per-claim support check puts A at 43.3% not-supported against C's 45.7%, a 2.4pp gap inside A's own 38pp rep-to-rep swing. **So the default stays because there is no stable positive result to move a reasoning default on, NOT because arm C was shown to be worse** — an important distinction if anyone reruns this. The knob is opt-in for a caller who has measured their own corpus. **Three lessons that generalise past this setting.** (1) The decision metric must be the fields the code branches on — `is_assertable` + `is_substantive`; mixing in `is_atomic` invented a self-inconsistency of 6.7% and changed the verdict on the first pass — **but "returned and read by no code" is not "harmless"**: the same call returns `atomic_theses`, and `candidates.extend(result.atomic_theses)` is the whole output, so an `is_atomic` disagreement reports that the arms cut the item differently and CANDIDATE YIELD is the instrument that catches what the gate rate cannot. (2) **A pairwise LLM judge carries two nuisance variables — set SIZE and set POSITION — and both were caught here.** Report the raw first-vs-second split (it swung 62/47/73% across runs), and prefer an UNPAIRED per-item rating when the question allows one: no other set to be longer than, no position to prefer, no tie to hide in, and a denominator in the hundreds instead of twelve. (3) **A verdict is provisional until it reproduces.** An endpoint that counts ties against detection is decided by the judge's tie rate, which is the least stable thing it does; pool runs before touching a default. Tests: `tests/test_thesis_extraction_step2_source.py` (20, both arms pinned equally, including that the arms differ in exactly one thing).

## Extraction faithfulness: ~35-39% not cleanly supported, 13% invented

**OPEN, and bigger than the setting above: roughly a THIRD of what step 2 emits is not cleanly supported by its own source, and the instrument saying so is now VALIDATED.** The unpaired per-claim check built for that A/B rated every candidate against the source on its own and returned **36 distorted + 16 invented of 120 claims for the shipped default path** (arm C the same shape, 45.7%). That was recorded here as an unvalidated LEAD; it is no longer one. `tests/e2e/probe_support_validity.py` spikes 84 claims of KNOWN ground truth into REAL batches of arm-A output, judged by the same imported `_support` in the same call as the real claims (a homogeneous control set does not transfer, because `_support` batches a whole candidate list into one call and a claim is judged among its neighbours): **specificity 93% (28/30) [0.79,0.98], sensitivity 100% (45/45) [0.92,1.00]**, verbatim floor 18/18 against a pre-registered 90%, verdict FIT TO QUOTE on pre-registered bands. **The strongest control cost nothing extra and is the one no argument about spike authorship can explain away:** every `foreign` spike IS another document's `verbatim` spike, so all 18 verbatim strings are judged twice with wording held exactly constant — once against the source that states them, once against one that does not — and the judge answered 18/18 supported vs 0/18. Rogan-Gladen corrects the recorded 43.3% to **39.3% [28.0,45.9]**, or **35.0%** if legitimate two-sentence synthesis counts as supported; that class is excluded from the registered primary and real extracted theses often ARE such joins, so **quote 35-39%, and note that pooling all three supported classes reads INDETERMINATE (87%) rather than FIT TO QUOTE** — the exclusion is load-bearing, not cosmetic.

**But the actionable result is that `distorted` and `invented` are NOT one instrument, so the 36 + 16 must not be corrected as one number.** `invented` attracted **ZERO of 39 truly-supported spikes** (0% [0.00,0.09], including every `combined`) while catching **27/27** truly-absent ones, so the **16 invented — 13.3% — needs no correction and is quotable as it stands**: that is content not in the source at all. Every false positive in the run was a `distorted` (5/39, 13%), so the **36 distorted (30%) corrects to 24.4%**. The two sum to ~38%, which is why the pooled figures bracket it. The named suspicion is CONFIRMED as the mechanism and sized: verbatim 100% vs compressed 83%, a +17pp gap against a pre-registered 15pp bar, and all five misses were stable across two byte-identical passes (`['distorted','distorted']` each), so this is a systematic reading of compression and synthesis, not judge noise. Test-retest 94% over 120 items; the spiked composition did not move the judge (11/36 [0.18,0.47] overlaps the recorded 52/120 [0.35,0.52], so the registered condition on transferring specificity back is NOT triggered). **So extraction quality is a real defect of the size the lead claimed, and the instrument is no longer the thing to doubt — but the correct target is `distorted`-class over-reading of compression, and the hard core is the 13% invented.** **The lesson that generalises past this finding: `probe_step2_isolate_ab.py` printed a RATE and persisted no per-item verdict, so the original 44% could not be audited at any price short of re-running it.** An instrument that emits a rate must persist per-item verdicts or its output is unfalsifiable by construction — which is also how this validation got its `combined` pricing, its per-label decomposition and its list of the five specific misjudged claims for free, after the run, with no further provider spend.
