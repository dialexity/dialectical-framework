## Two channels per scope

**Two channels per scope, and `Effect` stays a mutation.** `sid` carries `GraphEvent(effect=…)`; `sid:progress` carries `ProgressEvent` (`events/progress_event.py`, `bus.publish_progress`/`subscribe_progress`). Long chains that write no node until they finish — `TransformationGeneration` is 4 sequential calls, measured as 34s of dead air — report via `utils/progress.py`: `progress_scope(stage, key=…)` around the work, `report_progress(detail)` per step, `expect_progress(n)` to grow the denominator as work is discovered, and `note_progress(detail)` for the one shape a starting-step cannot describe (below). No-op with no scope installed. **Never widen `Effect`/`EffectType` for progress** — a separate channel is what lets an existing host upgrade without changes (pinned by `TestTheGraphChannelIsUntouched`). Two traps: the ContextVar holds a MUTABLE scope so gathered children share it, which means **a task created before the scope is installed reports nothing** (open the scope above the `gather`); and `detail` strings must carry no framework vocabulary, since a host may render them verbatim under the silent Advisor. `done` = steps ANNOUNCED (publish precedes increment, so a step that raises after announcing stays counted), `detail` = step just started, `total` grows — see the module docstrings before rendering any of it. **The closing (`final`) event carries an EMPTY `detail`.** It used to be `f"{stage} finished"`, which repeated `stage` as prose and leaked internal stage names to a person: `synthesis` is a BANNED word and `GenerateSynthesis` installs its own scope under the Advisor's `explore`, which owns none, so `"synthesis finished"` went out on the silent path — past three vocabulary tests, all of which had exempted `final` "by convention" precisely because the seam built it out of machinery. Every replacement wording is worse: naming the stage is machinery, and anything cheerful is a success claim `done` cannot back. So the closing label belongs to the HOST, which has `stage`, `key`, `done` and `total` to write it from; the three tests now cover every event and assert the closing detail is empty (`tests/test_progress.py::TestTheCountersTellTheTruth::test_the_closing_event_carries_no_label_of_its_own` pins it at the seam, so a regression fails even if it picks a word those tests do not ban).

## Instrumented stages, nesting, keys, and every tool's scope

**Instrumented stages:** `anchor`, `ingest`, `analysis`, `decision`, `deepen`, `synthesis`, `transformation`, `feasibility`, `edit`, `opposition`, `extraction`, `expansion` — where `synthesis` and `transformation` are the names a host sees only when those skills run OUTSIDE a tool that owns the stream (under `deepen` they defer and the stage reads `deepen`; see the nesting rule below). The keyed tool-level scopes (`anchor`, `ingest`) install at the TOOL and delegate to a split-out body, because the expensive work is inside gathers the tool creates — `ingest`'s are `SourceDigest`'s parts and `SurfaceTheses._sweep_windows`' windows, and it is what makes `AnalysisPipeline`'s pre-existing (previously silent) pair fire. Three rules the `ingest` work added, all pinned by `tests/test_ingest_progress.py`: **declare each step at its own site**, never up front — the closing event reports what COMPLETED and is not rounded up, so a step declared for a conditional phase that never runs looks exactly like one that failed; **report inside the semaphore**, so an event means "being read now" rather than "queued" (at a cap of 3 over 33 windows, queueing is most of the wait); and **indices only, never source content** — the unit of work on this path is a slice of the person's own file, so `f"Reading section {i} of {n}"`, never the window. `record_decision` (stage `decision`, keyed, tool-level) is the counter-example that fixes the rules' limit: it declares exactly ONE step, on the coherence check (~5.6s, the only stretch that produces nothing until it returns), because everything else the concern does is validation that refuses in-band and graph writes that already reach the host as effects on the `sid` channel — a second progress step for the same commit would tell the person their decision was saved twice. Its in-band refusals close at **0/0**, which is why `test_ingest_progress.py`'s `assert steps` vacuity guard does not transfer to that branch (`tests/test_decision_progress.py`). **`feasibility` is keyed by the pathways it audits, joined and sorted** — `",".join(sorted(t.short_hash for t in to_audit))`, not a digest of them. Two audits can be in flight (the person asks about one pathway, then another before the first returns, and the Advisor may spend both calls in one turn) and both used to publish under `feasibility`/`key=None`, so a host keying on `(stage, key)` folded two independent bars into one. The hashes go in RAW because the `_progress_key` digests elsewhere exist for input that is the person's own text; a short hash is already opaque, so digesting it hides nothing and costs a host its only way to line a bar up with the pathway asked about. Sorted so the same SET keys the same stream whatever order the model named them in, and drawn from `to_audit` rather than `targets` so the key and the denominator describe the same work (`tests/test_audit_feasibility_tool.py`). **One operation must have ONE label, and two sites now enforce that in code rather than by comment.** `placing_candidates_label(count)` in `concerns/thesis_extraction.py` is read by both `ThesisExtraction.resolve` (single window) and `SurfaceTheses._sweep_and_classify` (swept) — a person must not be able to read how large their source was off the label, and that was previously two comments asking two files to agree. `AUDITING_LABEL` in `concerns/transformation_audit.py` is read by both `explore`'s eager audit pass and `audit_feasibility`; they said "Checking the move against the situation" and "Checking whether the move is actually doable" for the identical `resolve(tr, input_text)` call, and since the tool SKIPS a pathway the eager pass already scored, the second wording made an already-done check look like a different, cheaper one. The doable wording won: it names what the person receives, not the method (`tests/test_transformation_audit_optional.py::TestBothCallersDescribeTheAuditTheSameWay`). **Pluralise only where the singular is reachable.** `find_polarities`' consolidation label reads "the N tensions", flat: it sits BELOW the `len(unique_hashes) < 2` guard, so N is always >= 2 and the "(s)" was hedging against a case the code returns before reaching. The two `placing_candidates_label` sites are the opposite — both slice a list that is legitimately 1 on a short source, so "1 candidate tension(s)" was reaching real people and the builder branches on the count. **`deepen` published two `final` events for one action; that is fixed, and the fix changed the seam's nesting rule.** It calls `ExploreTransformations` then `GenerateSynthesis` in sequence, each of which installs its OWN scope, so a host cleared its indicator when the transformation phase ended and then got a second indicator for synthesis. **The `anchor`/`ingest` shape did NOT transfer, and it is worth knowing why before anyone reaches for it again:** those two work because nothing beneath them installs a scope — the inner sites only call `report_progress`/`expect_progress`, which is exactly what makes `AnalysisPipeline`'s previously silent pair fire. Wrapping `deepen` that way would have produced THREE `final` events, since the old `progress_scope` installed unconditionally and its `finally` always published. Nor could the skills drop their scopes: each has THREE production call sites, six across the two (`ExploreTransformations`: `deepen`, `explorer.py`, its module-level helper; `GenerateSynthesis`: `deepen`, `explore`, the `generate_synthesis` tool) (`explore`, `explorer.py`, the `generate_synthesis` tool, the module-level helper), and every future caller would be silent by default. So the seam changed instead: **a nested `progress_scope` now DEFERS — it folds its `total` into the installed scope, yields that scope, and publishes no `final`; `stage` and `key` are discarded, because one tool call is one stream and the outer names it.** The module docstring's "INNERMOST SCOPE WINS, AND IT IS NOT A STACK" section is now "THE OUTERMOST SCOPE OWNS THE STREAM"; the old rule never described a real nesting in this tree — the only one was that defect. An already-closed outer scope is deferred to as well, which drops the inner events: the alternative is a fresh stream, `final` and all, after the tool has returned, which is the straggler case `report_progress` already refuses. `run_deepen` (not the `@llm.tool` wrapper, because `scoped.py`, the resume tests and the resume-hint pattern `build_status`'s docstring hands to host apps all enter here (`build_status` calls nothing itself; it recommends this shape, so a host following its advice becomes a caller)) installs `progress_scope("deepen", key=(wheel_hash or "").strip().strip("[]")[:7])` — the key is the short hash rather than a digest of it, since unlike `ingest` nothing here is the person's own text. **A progress key built from a tool ARGUMENT is built from raw model output, and must be sanitized like one.** The scope opens above any attempt to resolve the hash, and the framework renders hashes into prompts as `[[abc1234]]`, so a model echoing the brackets back — the most common malformed-hash shape in this tree, which is why `audit_feasibility` already strips them — keyed the stream `"[[a1b2"`: prompt-template punctuation in front of a person, and two spellings of ONE wheel getting two keys, which is the single thing a key exists to prevent. Only the KEY is sanitized, never the argument passed on — what a bad hash should do to the reasoning path is `ExploreTransformations`' decision. Pinned at both levels: `tests/test_progress.py::TestNestingDefersToTheInstalledScope` for the seam and `tests/test_advisor_deepen.py::TestOneDeepenIsOneProgressStream` through the tool, because a scope-object test cannot see the second `final` and a seam test cannot see whether a tool installed anything. **What that class does NOT show is that the two skills still open scopes of their own** — the scopes deferring in it are the STUBS', so a skill that dropped its `progress_scope` would leave it green; nothing pinned the real ones. Half of that is now closed: `test_tool_progress_scopes.py::test_the_reused_stage_names_are_safe_because_nesting_defers` drives the REAL `introduce_polarity` under an outer scope, which is what licenses the reused stage names below. The other half is closed too: `test_explore_progress_scope.py::TestTheTwoSkillsInstallTheirOwnScopes` drives both REAL skills — and the rule that came out of it, that a nesting test cannot pin the nested scope's EXISTENCE at all, is under `explore` below. **`explore` now owns its stream, and it took THREE doors because there are three ways in.** `run_exploration_detailed` (the shared body, NOT the `@llm.tool`, because two tool wrappers, `advisor.py`'s closing seam and four direct test/probe callers arrive there — one of them `probe_explore_progress.py` itself), `ExplorationPipeline.resolve()` (headless callers and the probes — it was an Explorer `explore` tool too, until that tool turned out to be in no toolset and was deleted; see below), and `BuildWheels.resolve()`. That third one is the easy miss and the reason to look for the pattern rather than the tool: **`build_wheels` is itself an `@llm.tool`**, and `report_progress` is a no-op with no scope installed, so its three labels would have been DEAD CODE on the one door where they are the only thing a person has to look at. Each is a `with progress_scope("exploration", key=…)` above a split-out body (`_run_exploration`, `_resolve`), split rather than indented for the seam's own reason — a task created before the scope is installed never sees it, and the gathers here are created inside the body. Nesting makes the inner ones DEFER, so one action is one stream whichever door it came through and the `2 x deep_wheels` finals are gone (the two skills were SIBLINGS, never nested — `ExplorationPipeline` used to close its scope before the synthesis loop started — which is why nothing below could fix this and the outer scope had to). Keys split the way the rest of the tree does. The Advisor door joins the SORTED short hashes of the perspectives being woven, `audit_feasibility`'s rule rather than `progress_key`'s: these are already opaque hashes the model read off its own prompt, so a digest hides nothing and costs a host its one way to line a bar up with the tensions the person just named. Each is sanitised individually with `progress_hash_key` because they are raw model output, the nexus is prefixed when there is one, and the key is computed from the CAPPED list so key and denominator describe the same work. **`intent` is deliberately NOT in that key** — free-form text in the person's own words, which would force a digest over the whole thing to keep it off a host's surface. The other two doors key on the nexus, the one node the person named to get here. Three labels, all of them inside `BuildWheels`: one before the combination phase, one per estimation pass, each declared inside its own guard so an empty pass declares no step (the phantom-step rule). **No step for the nexus create/expand phase, on evidence** — `CreateNexus.resolve()` is graph work with no provider call in it and every node and edge it writes already reaches the host as an effect on the `sid` channel, so a step there would report the one phase that needs no reporting. And estimation is TWO steps, not one per structure: `CausalityEstimation` gathers per (type, size) group, so per-structure steps would all carry one timestamp and say nothing (`note_progress`'s reasoning), while the group completions that could fill a fraction already write graph effects. Pinned by `tests/test_explore_progress_scope.py` (13 tests) and verified non-vacuous by mutation — replacing the three `with`s with `nullcontext` fails 3, 1 and 3 tests respectively. **The limit `deepen`'s class has is closed here rather than left open** (2026-09-10): `TestTheTwoSkillsInstallTheirOwnScopes` drives the REAL `ExploreTransformations` and `GenerateSynthesis` against a real Wheel, and "needs a committed Wheel with transitions and a full transformation run" turned out to cost ~3s per test under the mock brain. **THE RULE IT PRODUCED: A "NESTED SCOPE FOLDS IN" TEST CANNOT PIN THE NESTED SCOPE'S EXISTENCE, AND THE ONE THAT BITES MUST RUN THE SKILL WITH NO OUTER SCOPE.** Under a caller's scope, a skill whose `progress_scope` was deleted still publishes into the caller's stream and one-stage/one-key/one-final all still hold; the deletion shows up there only when the inner scope declared a `total` the caller's denominator then loses (`GenerateSynthesis`' `total=1` fails at 13/12, while `ExploreTransformations` declares none and its deletion stayed green — both measured). Two by-products worth keeping: **a door's closing event can outlive its own `resolve()`**, since `_publish` is `loop.create_task`, so a fixture that runs one door before subscribing must `await flush_progress()` or that stray `final` lands on the stream under test; and `synthesis` is both a real stage name and a BANNED label word, exempted in that file's `STAGES_EXEMPT_FROM_BANNED` rather than renamed, because a host may already key on it. **One phase would not yield soon enough on its own, and that took a fourth verb on the seam.** `flush_progress()` awaits `asyncio.sleep(0)` `_FLUSH_TURNS = 4` times and publishes nothing. Because `_publish` is fire-and-forget, a label announced immediately before a stretch that is SYNCHRONOUS all the way down is delivered only AFTER that stretch ends — the 0.0s flash again, and worse than silence here, because the label describes a wait that is already over. The combination phase is exactly that shape and it is the widest silence in this tree: 110.9s of a 163.2s k=4 wall with no event on either channel. So the rule is `report_progress(...)` then `await flush_progress()` immediately before a fully synchronous stretch, and NOWHERE else — everywhere else the next await is real work and a flush only delays it. **One turn would be enough to fix the TIMESTAMP** (that is when `_send` stamps the event) **but three is the measured floor for DELIVERY** — the `_send` task, the broadcaster backend's listener draining its published queue, then the subscriber's own queue — so the assertion is behavioural (a real bus, subscribed, event required to have ARRIVED when the flush returns) and it fails at 1 and at 2; the fourth turn is slack. **What `flush_progress` does NOT do is make the INSIDE of a synchronous stretch narratable** — steps announced from within it have the same delivery problem and no boundary left to flush at. **The inside needed a yield of its own, and the phase took it** (2026-09-10). `PerspectiveCombination.resolve` and `_build_layer` are now `async def` with `await asyncio.sleep(0)` after each cycle's wheels and after each layer's opposite-direction pass, which moved delivery from **0 of 1,750 effects before the phase returned to 1,459** (the remaining 291 are the estimation phase's). **The reading this kills is that the silence was a reporting cost: it was a scheduling artifact.** `ExecutionReport._emit` is `loop.create_task` too, so a phase that never yields writes an effect for every node and hands a host none of them — on the paid k=4 run, 1,629 effects in one burst after 12.8s of apparent quiet. **No label was added and none is wanted**: the phase writes 1,750 effects, so by `report_progress`'s own rule it owes no step; a step is for a wait that produces nothing to watch. Two things to know before touching it. **Correctness rests on WHERE the yields sit** — `_find_or_create_cycle` and the wheel branch of `_build_wheels_for_cycle` each query for an existing structure and then write one, and both are synchronous throughout, so no yield splits a check from its write and two concurrent explorations of one Nexus still cannot both create the "same" cycle; interleaving at these boundaries was already possible, since the caller awaits providers on either side of the phase. **And it costs a few percent rather than nothing** — three same-box k=4 runs (with / without / with) normalised against the harness-only `SET n:___DIALEXITY_TEST___` query, which no framework change can touch, put the combination phase at +2% and +6% and the wall at +3% and +5%, because the same 1,750 publish tasks now run INSIDE the phase's window instead of after it. Charges (67,556), structures (24 cycles / 96 wheels) and effect count are identical across all three. **Do not compare those walls to the 19.29s in `probe_build_wheels_offprovider.py`'s lever table** — that box ran the harness query at 1.24ms against 1.88-2.17ms now, so it is ~1.5x slower today for reasons no code here controls; same-session A/B or nothing. Pinned by `tests/test_graph.py::test_perspective_combination_delivers_effects_while_it_runs`, which subscribes a real bus and reads arrival times against the return instant — it fails at 0 delivered when the two `sleep(0)`s are removed, and a structural `iscoroutinefunction` check would not, since a coroutine that awaits nothing passes it and is one refactor away; it also asserts that reports are wired to the bus it subscribed to BEFORE it starts, because a leaked global mutes it into looking exactly like the defect (see the Testing section). `flush_progress` stays regardless: it guarantees the label leads the phase whatever the phase's internals do, and on a Nexus whose structures all already exist those yields have nothing to deliver. **But the yields moved the boundary its own test measures against, and left that test vacuous until it was rewritten.** `test_explore_progress_scope.py` compared the label's arrival to the instant `resolve` RETURNED, which was the whole defect while the phase never yielded; now a label published with no flush is delivered at the phase's FIRST internal yield, so deleting `await flush_progress()` left it green. It asserts against the phase's ENTRY instead (`test_the_combination_label_is_published_before_the_phase_starts`), where the mutation fails by 0.081s at k=2 — one cycle's worth of built structure. The transferable part: giving a phase a yield can silently weaken any assertion whose boundary was "before this returns".

## `ingest` verified live, and the holes it named

**`ingest`'s instrumentation is VERIFIED on the real path, and the live runs named what is still missing** (`probe_ingest_progress.py`, seven runs — three before the fixes below, four after). At 120 KB the sweep delivers what only a provider can show — a denominator known in advance and reported twice ("Reading part 3 of 4", "Reading section 3 of 4 for tensions") — closing at 23/23 with one key, exactly one terminal `final` event, no phantom steps and no content leaks, and the worst silent stretch cut from **52.3s graph-only to 14.4s**. Two numbers to carry rather than the wall clock: **total dead air barely moves (91% on that run; **but do not grade the channel on this figure at all** — see the correction two paragraphs down, and the seventh run's 81% -> 73%)** (the channel shortens the worst gap; it does not produce continuous motion), and the denominator's **worst backwards jump is 21%**, which is the live size of the caching caveat above. **Three holes the live runs found were all the same shape — one label announced before a gathered fan-out — and TWO are now closed** (`tests/test_ingest_progress.py::TestOneLabelNeverCoversAGatheredFanOut`). `ThesisExtraction.resolve` declares the classify phase, so the single-window path no longer bundles extraction + the step-2 gate + classification under one 12.2s label (27% of a 45.5s wall spent under a line saying "Reading the material for tensions" long after reading had finished); it uses `_extraction_sweep`'s wording verbatim, because the person should not be able to tell how large their source was from the vocabulary. `AntithesisExtraction.resolve`'s COMPLEX branch declares its last two links, which is the fix for the 14.4s hole and **the case that shows why "report per item" is not the general answer**: `find_polarities` gathers ten of these chains, so ten events at the gather would all carry the same timestamp and change nothing — links 2 and 3 stagger only because link N of one thesis starts when link N-1 of THAT thesis returns. Link 1 deliberately gets no step (it runs immediately after the caller's own announcement) and the SIMPLE branch gets none at all (one call, mechanical negation, under an announced phase) — `record_decision`'s rule, that a step is worth declaring only where the alternative is silence. **Both fixes are confirmed live, and the 1 KB pair is a real A/B** (45.9s against 45.5s, 70 calls and 245 effects both, 6.40x against 6.48x): worst gap **12.2s → 8.2s**, the bundled label cleanly split into 5.3s + 6.6s, closed 22/22. At 120 KB each new label fired 10x, the target hole went **14.4s → 6.6s** and it closed 44/44 — but that run drew 196 calls against 127, so **nothing about it is wall-clock comparable**. **The third is IRREDUCIBLE and is the floor, not a to-do** — `expand_polarities`' five ~11s tetrads, the widest hole of the 1 KB run. The advice once written here, that it "would need per-CALL subdivision as `TransformationGeneration` has", was wrong and was retracted by reading the code: on this path `AspectGeneration.resolve` takes the four-position branch into `_generate_tetrad`, which is ONE `TetradDto` call for all of T+/T-/A+/A-, so there is no chain to subdivide. Nor does completion reporting help: the five start within 0.2s of each other and return within 1.5s of each other, and the graph effects they write land at the same moment as the first completion, so a note would arrive on top of an event the host already has. Subdividing it means splitting one provider call into four — a reasoning change, not instrumentation.

Three things the after runs settled that are easy to get wrong. **The 21% backwards jump did NOT grow, and the prediction here that it would was wrong**: it is set by the EARLIEST growth, when the denominator is smallest (2 → 7), so additive growth later at a `total` in the forties cannot beat it — declaring more steps mid-run is cheap in this respect. **Dead air is the wrong figure to grade this channel on**: it reads 91% → 86% at 120 KB but the absolute number is 90.8s → 90.5s (the wall grew), and at 1 KB it goes the other way, 73% → 82%, because the identical 245 effects arrived in 8 graph bursts instead of 6. Grade it on the worst gap, the only figure the channel can move. And **a retry is invisible on this channel** — the first retrying run (`retries 1 {'parse': 1}`) doubled one digest part with no event saying so, which is correct by design (`_progress_key` is content-derived precisely so a retry is not new work) but means any single gap may be a retry rather than a slow call. That retry also promoted a FOURTH instance of the same shape to widest hole of the 120 KB run: **`SourceDigest`'s parts, 25.4s** (four single calls announced together, then silence until the reduce). It needed a THIRD verb on the seam, because nothing about a *starting* step describes N gathered single calls — they all start at one instant and each is one call, so the only remaining fact is when they come BACK. `note_progress(detail)` publishes the counters UNCHANGED with `ProgressEvent.note=True`, so a host refreshes its label and leaves its bar where it is.
